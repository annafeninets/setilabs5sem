# setilab2 — передача файла по TCP с подсчётом скорости

Приложение реализует свой протокол передачи произвольного файла с одного
компьютера на другой поверх TCP. Сервер принимает несколько клиентов
одновременно (по потоку на клиента), сохраняет полученные файлы в `uploads/`
и раз в 3 секунды выводит мгновенную и среднюю скорость приёма отдельно для
каждого активного клиента. Приложение кроссплатформенное: сеть работает как
через POSIX-сокеты (Linux/macOS), так и через Winsock2 (Windows/MSVC) —
переключение делается автоматически в `common/platform.hpp` по `#ifdef _WIN32`.

## Структура проекта

```
setilab2/
├── common/
│   ├── platform.h[pp/cpp]      # Winsock2 vs POSIX-сокеты, единые обёртки для обеих ОС
│   ├── socket.hpp              # RAII-обёртка над сокетом (закрытие при выходе из области видимости)
│   ├── connection_error.hpp    # исключение для ошибок сети/протокола
│   ├── logger.hpp              # потокобезопасный вывод в консоль
│   ├── protocol_limits.hpp     # лимиты протокола: 4096 байт на имя, 1 ТиБ на размер файла
│   ├── display_units.hpp       # байты -> мегабайты только для вывода в консоль
│   ├── utf8.h/.cpp             # проверка, что строка — корректный UTF-8
│   └── tcp_connection.h/.cpp   # протокол поверх TCP (см. ниже)
├── client/
│   ├── file_client.h/.cpp     # класс FileClient: подключение и отправка файла
│   └── main.cpp                # точка входа клиента: разбор аргументов
├── server/
│   ├── server.h/.cpp           # accept-цикл, по потоку на клиента
│   ├── client_session.h/.cpp   # приём одного файла, защита от выхода за uploads/
│   ├── speed_tracker.h/.cpp    # отдельный поток с отчётом о скорости раз в 3 с
│   └── main.cpp                 # точка входа сервера: разбор аргументов
├── CMakeLists.txt
└── README.md
```

## Протокол

Клиент → сервер, одной сессией на одно TCP-соединение:

| Поле              | Тип                            |
|-------------------|---------------------------------|
| длина имени файла | `uint64`, big-endian             |
| имя файла         | UTF-8, без завершающего нуля     |
| размер файла      | `uint64`, big-endian             |
|  содержимое файла | поток байт ровно `размер файла`  |

Сервер → клиент, после приёма и проверки всего файла:

| Поле         | Тип                             |
|--------------|-----------------------------------|
| длина строки | `uint64`, big-endian               |
| строка       | `"SUCCESS"` или `"FAIL"`           |

## Сборка

### CMake (CLion или консоль, любая ОС)

```bash
cmake -S . -B cmake-build-debug
cmake --build cmake-build-debug
```
Исполняемые файлы — `cmake-build-debug/server` и `cmake-build-debug/client`
(на Windows — `server.exe` / `client.exe`, обычно в подпапке `Debug`/`Release`).

### Вручную через g++ (Linux/macOS)

В корне проекта уже есть каталоги `server/` и `client/` с исходниками —
поэтому бинарники нужно класть не в корень (иначе `-o server` упрётся в
`cannot open output file server: Is a directory`), а, например, в `bin/`:

```bash
mkdir -p bin

g++ -std=c++17 -Wall -Wextra -O2 -pthread \
    server/main.cpp server/server.cpp server/client_session.cpp server/speed_tracker.cpp \
    common/tcp_connection.cpp common/platform.cpp common/utf8.cpp \
    -o bin/server

g++ -std=c++17 -Wall -Wextra -O2 -pthread \
    client/main.cpp client/file_client.cpp \
    common/tcp_connection.cpp common/platform.cpp common/utf8.cpp \
    -o bin/client
```

## Запуск

```bash
./bin/server <port>
./bin/client <путь-к-файлу> <host-или-IP-сервера> <port>
```

Пример работы:

```bash
./bin/server 9090
```

## Константы и явные проверки требований задания

| Константа/проверка                | Где объявлена                     | Значение         | Что именно проверяет                                                                 |
|-------------------------------------|------------------------------------|-------------------|-----------------------------------------------------------------------------------------|
| `kChunkSize`                        | `client/file_client.cpp`, `server/client_session.cpp` | 65536 (64 КиБ) | размер одного блока при чтении файла и передаче по сети                                |
| speed-report interval               | `server/speed_tracker.cpp`          | 3 секунды         | период вывода мгновенной/средней скорости на сервере                                   |
| `kMaxFileNameBytes`                 | `common/protocol_limits.hpp`        | 4096 байт         | максимальная длина имени файла; проверяется и клиентом (`FileClient::sendFile`), и сервером (`TcpConnection::recvString`) |
| `isValidUtf8(...)`                  | `common/utf8.hpp` / `.cpp`          | —                 | что имя файла — корректный UTF-8, а не просто байтовая строка нужной длины; проверяется и клиентом (до отправки), и сервером (после приёма, сервер не доверяет клиенту) |
| `kMaxFileSizeBytes`                 | `common/protocol_limits.hpp`        | 1 ТиБ = 2^40 байт | максимальный размер файла; проверяется и клиентом (перед отправкой), и сервером (сразу после приёма заголовка, до начала записи на диск) |
| `kBytesPerMegabyte`                 | `common/display_units.hpp`          | 1 000 000 (10^6)  | единица пересчёта только для консольного вывода (`server/client_session.cpp`, `server/speed_tracker.cpp`) — сам подсчёт скорости и лимиты по-прежнему в байтах |
| `kMaxConcurrentClients`             | `server/server.cpp`                 | 10                | сколько клиентов сервер обслуживает параллельно; сверх лимита новое соединение сразу закрывается без создания потока |
| `kIoTimeoutSeconds`                 | `common/protocol_limits.hpp`        | 30 секунд         | таймаут на каждый `recv()`/`send()` (`SO_RCVTIMEO`/`SO_SNDTIMEO`) и на клиенте, и на сервере: зависший собеседник не блокирует программу навсегда |
| `kStatusSuccess` / `kStatusFail`    | `common/protocol_limits.hpp`        | `"SUCCESS"`/`"FAIL"` | статус ответа сервера; `FAIL` сервер отправляет и при отказе из-за лимита клиентов |
| `kAcceptRetryDelay`                 | `server/server.cpp`                 | 100 мс            | пауза после неудачного `accept()`, чтобы постоянная ошибка не крутила цикл вхолостую |

Каждая из этих проверок явно прокомментирована в коде ссылкой на конкретный
пункт задания (`// Требование: ...`) — см. `client/file_client.cpp`,
`server/client_session.cpp` и соответствующие заголовки.

## Тестирование на трёх виртуальных машинах (Oracle VirtualBox)

Проверялось на трёх клонированных Ubuntu-VM,
объединённых внутренней сетью VirtualBox (`Internal Network`, `lab-net`) плюс
NAT-адаптером для интернета и проброшенными SSH-портами с хоста.

| VM   | IP              | SSH-порт (host) | Роль в тесте                          |
|------|-----------------|------------------|-----------------------------------------|
| vm1  | 192.168.100.10  | 2222             | сервер (`./build/server 9090`)          |
| vm2  | 192.168.100.11  | 2223             | клиент №1                               |
| vm3  | 192.168.100.12  | 2224             | клиент №2                               |

*(IP/порты — из окружения; если у вас другие адреса, подставьте свои.)*

Единственное, стоит проверить перед тестом — открыт ли порт сервера в файрволе гостевой ОС:

```bash
# на vm1, если ufw активен
sudo ufw allow 9090/tcp
```
## Имена файлов длиннее предела файловой системы

По условию имя может быть до 4096 байт, а файловая система обычно принимает
не более 255 (`NAME_MAX`). Сервер узнаёт реальный предел для каталога
`uploads/` через `pathconf(_PC_NAME_MAX)` (вручную: `getconf NAME_MAX uploads`)
и, если имя длиннее, сохраняет укороченное: расширение сохраняется, обрезка
идёт по границе UTF-8 символа (`truncateUtf8`), так что имя остаётся валидным.
Имя с нулевым байтом сервер отклоняет как ошибку клиента.
