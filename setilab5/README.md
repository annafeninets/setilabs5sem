# lab5 — SOCKS5-прокси

Прокси-сервер по стандарту **SOCKS версии 5** (RFC 1928). Поддерживается команда
`CONNECT` (TCP-соединение), адреса **IPv4** и **доменные имена**; аутентификация и
IPv6 не реализуются. В параметрах передаётся только порт, на котором прокси ждёт клиентов.

## Как это работает

- Один поток, все сокеты неблокирующие, ожидание событий — `epoll`. Блокируется
  программа только в `epoll_wait`, дополнительных потоков нет.
- Рукопожатие: приветствие (метод «без аутентификации», `0x00`) -> запрос `CONNECT`
  -> ответ прокси -> пересылка данных. Прокси ничего не предполагает о протоколе
  внутри соединения, данные идут в обе стороны одновременно.
- **Резолвинг имён** (ATYP `0x03`) тоже неблокирующий: при старте создаётся UDP-сокет,
  он добавлен в `epoll` на чтение. Для имени отправляется DNS-запрос A-записи
  рекурсивному резолверу (адрес берётся из `/etc/resolv.conf`), ответ разбирается
  в обработчике чтения сокета, после чего начинается `connect()`. Ответ сопоставляется
  с запросом по id и имени; таймаут — 5 с; если у имени несколько A-записей и первая
  не подошла, пробуются следующие.
- **Аккуратное закрытие**: когда одна сторона закончила передачу (FIN), после доставки
  всех накопленных данных второй стороне отправляется `shutdown(SHUT_WR)`; соединение
  закрывается, только когда завершены оба направления.
- **Память на клиента ограничена**: два буфера по 64 КБ (по одному на направление).
  Пока буфер полон, чтение из сокета-источника отключается — работает обычное
  TCP-давление, быстрый отправитель не раздувает память.
- **Нет холостых циклов**: интерес к `EPOLLIN`/`EPOLLOUT` пересчитывается после каждого
  события — читаем, только если есть место в буфере, пишем, только если есть данные.
  Сокет, у которого ничего ждать не нужно, снимается с `epoll` (иначе `EPOLLHUP`
  будил бы цикл бесконечно). При нехватке дескрипторов (`EMFILE`) приём новых клиентов
  приостанавливается до закрытия какого-либо соединения.
- Коды ответов: `0x00` успех, `0x01` общий сбой, `0x02` запрещено, `0x03` сеть недоступна,
  `0x04` хост недоступен (в т.ч. имя не найдено / DNS не ответил), `0x05` отказ в соединении,
  `0x06` таймаут, `0x07` команда не поддерживается (`BIND`, `UDP ASSOCIATE`),
  `0x08` тип адреса не поддерживается (IPv6).

## Структура проекта

```
lab5_cpp/
├── main.cpp         # разбор аргумента (порт), создание и запуск Server
├── server.hpp/cpp   # Server: слушающий сокет, приём клиентов, владение сессиями, главный цикл
├── session.hpp/cpp  # Session: одно клиентское соединение (рукопожатие, connect, пересылка)
├── resolver.hpp/cpp # DnsResolver: неблокирующий DNS-клиент на UDP-сокете
├── socks5.hpp/cpp   # формат протокола SOCKS5: разбор запросов, построение ответов (без сокетов)
├── dns.hpp/cpp      # формат DNS-сообщений: запрос A-записи, разбор ответа, адрес резолвера
├── epoll.hpp/cpp    # EventHandler (интерфейс), Epoll, Watch (подписка сокета на события)
├── fd.hpp           # FileDescriptor: RAII-владелец файлового дескриптора
├── buffer.hpp       # Buffer: буфер фиксированной ёмкости на одно направление
├── CMakeLists.txt
├── Makefile
└── README.md
```

## Сборка

Нужны `g++` (C++17) и `make` (на VM: `sudo apt install build-essential`).

### Make

```bash
make
```
Исполняемый файл — `./socks5_proxy`.

### CMake

```bash
cmake -S . -B cmake-build
cmake --build cmake-build
```
Исполняемый файл — `cmake-build/socks5_proxy`.

### Вручную через g++

```bash
g++ -std=c++17 -Wall -Wextra -O2 *.cpp -o socks5_proxy
```

## Запуск

```bash
./socks5_proxy <порт>
```

Пример:
```bash
./socks5_proxy 1080
```

Вывод (в stderr). Каждая строка про клиента начинается с его адреса `[ip:порт]`;
ошибки помечены `ERROR`:
```
DNS resolver 127.0.0.53
SOCKS5 proxy listening on port 1080
resolve example.com
[192.168.100.11:51234] connected to example.com:80 (8.47.69.0:80)
resolve no-such-host.invalid
ERROR: resolve no-such-host.invalid: DNS error (rcode 3, NXDOMAIN)
[192.168.100.11:51240] ERROR: cannot resolve no-such-host.invalid (reply 0x04)
[192.168.100.11:51246] ERROR: cannot connect to 192.168.100.12:9: Connection refused (reply 0x05)
```

Что попадает в лог при ошибках: имя не найдено / DNS не ответил (таймаут 5 с), отказ или
недоступность цели (с текстом ошибки `connect`), неподдерживаемая команда или тип адреса,
отсутствие метода «без аутентификации», нарушение протокола (например, клиент не SOCKS5),
уход клиента на этапе рукопожатия, ошибки чтения/записи в соединении, ошибка `accept`.

На Ubuntu в `/etc/resolv.conf` обычно стоит `127.0.0.53` (локальный кэш systemd-resolved) — он принимает UDP-запросы, прокси работает с ним как есть.

Адрес DNS-резолвера можно переопределить переменной окружения (нужно для отладки):
```bash
SOCKS_DNS=8.8.8.8 ./socks5_proxy 1080
```

## Настройки

| Константа      | Где              | Значение | Назначение                                         |
|----------------|------------------|----------|----------------------------------------------------|
| `kBufSize`     | `session.cpp`    | 64 КБ    | размер буфера одного направления на одного клиента |
| `kMaxEvents`   | `epoll.cpp`      | 256      | сколько событий забирается из `epoll_wait` за раз  |
| `kMaxAddrs`    | `resolver.cpp`   | 8        | сколько A-записей из DNS-ответа используется       |
| `kTimeout`     | `resolver.cpp`   | 5 с      | время ожидания DNS-ответа                          |

## Тестирование на трёх виртуальных машинах (Oracle VirtualBox)

Используются три Ubuntu-VM во внутренней сети VirtualBox (`Internal Network`, `lab-net`)
+ NAT-адаптер для доступа наружу и проброшенные SSH-порты.

| VM  | IP              | SSH-порт (host) | Роль в тесте          |
|-----|-----------------|-----------------|-----------------------|
| vm1 | 192.168.100.10  | 2222            | прокси                |
| vm2 | 192.168.100.11  | 2223            | клиент (curl)         |
| vm3 | 192.168.100.12  | 2224            | второй клиент / «сервер» |

### 1. Подготовка (на каждой VM, сбрасывается после перезагрузки)

```bash
sudo ip route add 224.0.0.0/4 dev enp0s3
```
Для прокси важно лишь, чтобы vm1 имела выход наружу (NAT-адаптер) и видела vm2/vm3
по внутренней сети. Если на vm1 включён `ufw`, откройте порт:
```bash
sudo ufw allow 1080/tcp
```

### 2. Копирование и сборка на vm1

С хост-машины:
```bash
scp -P 2222 -r lab5_cpp <user>@127.0.0.1:~/
ssh -p 2222 <user>@127.0.0.1
```
На vm1:
```bash
cd ~/lab5_cpp && make
./socks5_proxy 1080
```

### 3. Проверка с vm2 (или vm3)

```bash
# адрес IPv4 (резолвит клиент); IP возьмите из лога прокси после предыдущего запроса
# (строка «connected to example.com:80 (<IP>:80)»); адреса example.com со временем меняются.
# Заголовок Host нужен: Cloudflare отвечает 403 (error 1003) на запросы к голому IP
curl -v --socks5 192.168.100.10:1080 -H 'Host: example.com' http://8.47.69.0/

# имя резолвит прокси (ATYP 0x03) — проверка неблокирующего DNS
curl -v --socks5-hostname 192.168.100.10:1080 http://example.com/

# HTTPS (прокси не смотрит внутрь соединения)
curl -v --socks5-hostname 192.168.100.10:1080 https://example.com/
```
Ожидаемо: страница загружается, в логе vm1 видны строки `resolve ...` и `connected to ...`.
Результат прогона на vm2 -> vm1: HTTP и HTTPS (TLS 1.3, HTTP/2) загружаются, несуществующее имя даёт
ошибку 4, закрытый порт — ошибку 5.

Дополнительно:
```bash
# несуществующее имя -> ошибка 4 (host unreachable)
curl -sS --socks5-hostname 192.168.100.10:1080 http://no-such-host.invalid/

# закрытый порт -> ошибка 5 (connection refused)
curl -sS --socks5 192.168.100.10:1080 http://192.168.100.12:9/

# скорость: прокси не должен быть заметно медленнее прямого соединения
curl -o /dev/null -w '%{speed_download}\n' http://<файл>
curl -o /dev/null -w '%{speed_download}\n' --socks5-hostname 192.168.100.10:1080 http://<файл>
```

### 4. Проверка в браузере

С хоста пробросьте порт прокси через проброшенный SSH-порт vm1:
```bash
ssh -p 2222 -N -L 1080:127.0.0.1:1080 <user>@127.0.0.1
```
В настройках браузера укажите SOCKS5-прокси `127.0.0.1:1080` (в Firefox ещё включите
«Proxy DNS when using SOCKS v5», чтобы имена резолвил прокси). Откройте сайт, богатый
контентом, и сравните время загрузки на вкладке **Network** (Developer tools) с прямым
подключением.
